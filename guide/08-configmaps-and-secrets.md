# 08 · ConfigMaps and Secrets

🟡 Intermediate · ⏱️ 30 min · [← Previous](07-services-and-dns.md) · [Home](../README.md) · [Next: Health probes and resources →](09-health-probes-and-resources.md)

## Build once, configure per environment

The same image should run in dev, staging and production. Everything that differs (URLs, log levels, feature flags, passwords) is injected at runtime. This is the [12-factor app](https://12factor.net/config) principle, and Kubernetes provides two objects for it:

| | ConfigMap | Secret |
|---|---|---|
| For | Non-sensitive configuration | Passwords, tokens, keys, certificates |
| Stored as | Plain text in etcd | base64 in etcd (**encoding, not encryption!**), optionally encrypted at rest |
| Access control | Normal RBAC | Normally restricted by RBAC more tightly |
| Size limit | 1 MiB | 1 MiB |

## ConfigMap

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  LOG_LEVEL: INFO
  LLM_URL: http://llm:11434
  settings.toml: |              # a whole file as one key
    [summary]
    window_hours = 168
```

```bash
# or generate it
kubectl create configmap app-config --from-literal=LOG_LEVEL=INFO --from-file=settings.toml --dry-run=client -o yaml
```

## Secret

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: db-credentials
type: kubernetes.io/basic-auth   # a well-known type with "username" and "password" keys
stringData:                      # write plain text here; the API stores it base64-encoded under "data"
  username: ingestor
  password: s3cr3t
```

```bash
kubectl create secret generic db-credentials --from-literal=username=ingestor --from-literal=password="$(openssl rand -hex 16)"
kubectl get secret db-credentials -o jsonpath='{.data.password}' | base64 -d   # anyone with read access can do this
```

## Using them in pods

```yaml
spec:
  containers:
    - name: app
      image: myapp:1.0
      envFrom:                        # (1) every key becomes an env var
        - configMapRef:
            name: app-config
      env:
        - name: DB_PASSWORD           # (2) a single key, from a Secret
          valueFrom:
            secretKeyRef:
              name: db-credentials
              key: password
      volumeMounts:                   # (3) as files
        - name: config
          mountPath: /etc/app
          readOnly: true
  volumes:
    - name: config
      configMap:
        name: app-config              # /etc/app/LOG_LEVEL, /etc/app/settings.toml, ...
```

| Method | Updates while the pod runs? | Good for |
|---|---|---|
| Environment variables | ❌ Read once at container start | Simple settings (most apps) |
| Mounted files | ✅ Refreshed after a short delay (not with `subPath`) | Config files, certificates the app re-reads |

### The "I changed the ConfigMap but nothing happened" problem

Pods read env vars at start. Changing a ConfigMap does **not** restart pods. Options:

1. `kubectl rollout restart deployment/app` after every change (manual and easy to forget).
2. **Better:** let Kustomize's `configMapGenerator` append a content hash to the name (`app-config-7b5g2kt8f4`). A change produces a new name, which changes the pod template, which triggers a normal rolling update. Old ReplicaSets keep pointing to the old ConfigMap, so even `rollout undo` restores the old config.

> 🔗 **In the project:** [`skypulse/k8s/base/kustomization.yaml`](../skypulse/k8s/base/kustomization.yaml) generates `analysis-config-<hash>` and `ingestor-config-<hash>` from plain `.env` files. Change `SUMMARY_WINDOW_HOURS` in [`analysis/config.env`](../skypulse/k8s/base/analysis/config.env), run `make deploy`, and watch the api and analyzer roll.

## Secrets: what "secret" really means

Out of the box, a Secret is only as safe as:

1. **RBAC**: who may `get`/`list` secrets in the namespace. Note that anyone who can create a pod in a namespace can mount its secrets.
2. **etcd encryption at rest**: off by default in upstream Kubernetes. k3s enables it with `--secrets-encryption`.
3. **Not committing them to Git.** Never put a plain Secret manifest in a repository.

How teams handle secrets in Git-driven workflows:

| Approach | How it works |
|---|---|
| **Generated in-cluster** | Something inside the cluster creates the secret. Operators (like CloudNativePG) generate their own credentials. |
| **Sealed Secrets** | Encrypt with the cluster's public key; the encrypted file is safe to commit; a controller decrypts it in-cluster. |
| **SOPS** (+ age/GPG/KMS) | Encrypt values in YAML files; decrypt at deploy time (Argo CD/Flux plugins). |
| **External Secrets Operator** | Sync from Vault, AWS/GCP/Azure secret managers, 1Password… into Kubernetes Secrets. |
| **Vault agent / CSI driver** | Mount secrets directly from Vault without a Kubernetes Secret object. |

> 🔗 **In the project:**
> - The schema owner's password is **generated by the CloudNativePG operator** into the Secret `feeddb-app` in the `skypulse-data` namespace. No human ever sees it, and only the migration Job in that same namespace uses it.
> - Each application zone logs in with its own least-privilege role (`ingestor`, `analysis`). Those passwords are **generated by `make secrets`** (random, stored in the git-ignored `.secrets/` folder). Each one is created in *two* namespaces, the data namespace (where the operator creates the role) and the zone's own namespace (where the pods log in), because a pod can only read Secrets from its own namespace. In production you'd use External Secrets or Sealed Secrets instead.

## Downward API: information about the pod itself

```yaml
env:
  - name: POD_NAME
    valueFrom: { fieldRef: { fieldPath: metadata.name } }
  - name: NODE_NAME
    valueFrom: { fieldRef: { fieldPath: spec.nodeName } }
  - name: MEMORY_LIMIT
    valueFrom: { resourceFieldRef: { resource: limits.memory } }
```

## Try it

1. Create a ConfigMap with `GREETING=hello`, a Deployment that runs `sh -c 'echo $GREETING; sleep 3600'` with `envFrom`, and check the logs.
2. Change the ConfigMap. Do the logs change? (No.) Now `kubectl rollout restart` and check again.
3. Mount the ConfigMap as a volume instead, `cat` the file, change the ConfigMap and wait about a minute. The file updates without a restart.

## Key takeaways

- **ConfigMap** for settings, **Secret** for credentials; inject them as env vars or files.
- Env vars don't update in running pods. Use hashed ConfigMap names (Kustomize) to roll automatically.
- Secrets are base64, not encrypted. Protect them with RBAC and encryption at rest, and keep them out of Git (or encrypt them).
