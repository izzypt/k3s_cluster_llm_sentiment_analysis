# `skypulse-data`: the data tier (plus `cnpg-system`)

Zones: [index](../README.md) · [outside](../outside/README.md) · [your machine](../your-machine/README.md) · [ingestion](../ingestion/README.md) · **data** · [analysis](../analysis/README.md) · [monitoring](../monitoring/README.md) · [system](../system/README.md)

## What this namespace does

It holds **the only state in the system**: a PostgreSQL database with three tables (`subscriptions`, `posts`, `summaries`). Every other component is stateless, which is what lets Kubernetes kill, move and replace them freely.

It's also **where the two application zones meet**. The ingestor writes posts, the analyzer reads and classifies them, and the api reads the summaries. They never talk to each other directly, only through rows here. Each logs in as its own least-privilege role.

The database is run by the **CloudNativePG (CNPG) operator**, which lives in its own namespace, `cnpg-system`, but exists only to serve this one. It's covered here.

### Credentials stay here

The **schema owner's** credentials (Secret `feeddb-app`, generated by CNPG) exist only in this namespace and are used only by the migrate Job. The app zones get their own limited users (`ingestor`, `analysis`), whose passwords `make secrets` writes into both this namespace (so CNPG can create the user) and the zone's own namespace (so the Pods can log in) ([`Makefile` L93-L109](../../../skypulse/Makefile#L93-L109)). This separation is why the database has its own namespace (DESIGN.md D-10).

### Who may do what in the database ([`db.py` L109-L135](../../../skypulse/src/skypulse/db.py#L109-L135))

| Role | Used by | Granted |
|---|---|---|
| `skypulse` (owner) | migrate Job | Everything: creates the schema |
| `ingestor` | ingestor | Read targets, record poll status, insert posts |
| `analysis` | api, analyzer | Manage subscriptions, read posts, write sentiment and summaries. No schema changes. |
| `pg_monitor` | the metrics exporter | Read timestamps and counters only, never post texts or summaries |

## The components

### DB primary

The PostgreSQL instance that accepts writes. All clients connect to the Service **`feeddb-rw`**, which CNPG always points at the current primary, so clients never need to know which Pod that is. TLS is on by default (clients use `PGSSLMODE=require`).

**The schema** (migration 1, [`db.py` L21-L65](../../../skypulse/src/skypulse/db.py#L21-L65)):

- `subscriptions`: what to follow (`kind` = handle/hashtag, `value`), plus `last_polled_at` and `last_error` from the ingestor.
- `posts`: fetched posts. **`analyzed_at IS NULL` means "waiting for the LLM"**, so this table is also the work queue (D-2). `UNIQUE(subscription_id, uri)` makes ingestion idempotent; the partial index `posts_unanalyzed` keeps the queue query fast.
- `summaries`: one row per subscription: the LLM summary, overall label, counts, window and `updated_at`.

**Monitoring.** Each instance runs a metrics exporter on :9187. Besides standard PostgreSQL health metrics, it runs SkyPulse's own SQL ([`monitoring-queries.yaml`](../../../skypulse/k8s/base/data/monitoring-queries.yaml)) on every scrape and publishes the results as metrics: backlog (`posts_pending`), age of the oldest pending post, summary age per subscription, and failing subscriptions. The pipeline hands work over through the database, so the database already knows whether the system is healthy. These queries run on the primary only (`primary: true`), so each value is reported once.

### DB replica

A **streaming replica**: it continuously receives the primary's write-ahead log (WAL), the log of every change, and replays it.

- It runs on **a different node** from the primary, enforced by required anti-affinity ([`postgres.yaml` L44-L47](../../../skypulse/k8s/base/data/postgres.yaml#L44-L47)). One node failure can't take out both copies.
- **Failover:** if the primary dies, CNPG promotes the replica and moves `feeddb-rw` to it. Clients reconnect: the api's connection pool checks connections before use, and the workers catch the error and reconnect. *Measured:* deleting the primary caused 0 failed api requests.
- Read-only Services `feeddb-ro`/`feeddb-r` exist too, but SkyPulse doesn't use them.
- Locally there are 2 instances ([`postgres.yaml` L17](../../../skypulse/k8s/base/data/postgres.yaml#L17)); production runs 3 with 50 Gi each ([production overlay](../../../skypulse/k8s/overlays/production/kustomization.yaml#L22-L30)).

⚠️ **A replica is not a backup.** A bad `DELETE` or migration is copied to the replica too. Backups are an open item (DESIGN.md §5 #2).

### migrate Job

Sets up what's inside the database: the tables, and what each user may do.

- **Runs** the shared image with `args: ["migrate"]` ([`migrate.yaml` L36](../../../skypulse/k8s/base/data/migrate.yaml#L36)), with `DATABASE_URL` taken from CNPG's owner Secret `feeddb-app` ([L38-L42](../../../skypulse/k8s/base/data/migrate.yaml#L38-L42)).
- **What `migrate()` does** ([`db.py` L86-L136](../../../skypulse/src/skypulse/db.py#L86-L136)):
  1. waits for the database;
  2. takes an **advisory lock** ([L94](../../../skypulse/src/skypulse/db.py#L94)), so two migrations can never run at the same time;
  3. applies any migration not yet listed in `schema_migrations`, each in its own transaction (**idempotent**: running it again changes nothing);
  4. re-applies the **GRANTs** for `ingestor`, `analysis` and `pg_monitor`. `_grant()` ([L139-L152](../../../skypulse/src/skypulse/db.py#L139-L152)) first waits for CNPG to create each user.
- **When it runs:** on every deploy. `make deploy` deletes the old Job and waits for it to finish before the rollouts. In production it's an Argo CD **Sync hook** ([`migrate.yaml` L16-L18](../../../skypulse/k8s/base/data/migrate.yaml#L16-L18)). `backoffLimit: 10` covers a database that is still starting.
- **Rule:** migrations must be backward compatible (expand → contract), because old and new app versions run side by side during a rolling update (D-8).

### CNPG operator (namespace `cnpg-system`)

A Kubernetes **operator**: a controller that watches the custom `Cluster` object ([`postgres.yaml`](../../../skypulse/k8s/base/data/postgres.yaml)) and does the database administration. From about 30 lines of YAML it creates and runs:

| You write | CNPG makes it real |
|---|---|
| `instances: 2` ([L17](../../../skypulse/k8s/base/data/postgres.yaml#L17)) | Primary and replica Pods, one PVC each, streaming replication |
| `bootstrap.initdb` ([L22-L25](../../../skypulse/k8s/base/data/postgres.yaml#L22-L25)) | Database `skypulse`, owner `skypulse`, Secret `feeddb-app` |
| `managed.roles` ([L30-L41](../../../skypulse/k8s/base/data/postgres.yaml#L30-L41)) | The `ingestor` and `analysis` login users, with passwords from their Secrets (no permissions until migrate grants them) |
| *(automatic)* | Services `feeddb-rw`, `feeddb-ro`, `feeddb-r`; TLS certificates; failover |
| `monitoring` ([L59-L62](../../../skypulse/k8s/base/data/postgres.yaml#L59-L62)) | The exporter on :9187, running the custom queries |

Installed by `make operator` from the upstream release manifest (pinned version, [`Makefile` L22-L23](../../../skypulse/Makefile#L22-L23)). Why an operator rather than a hand-written StatefulSet: a StatefulSet gives you storage, but not failover (DESIGN.md D-3).

## How it handles failure

| What happens | Result |
|---|---|
| Primary Pod or node dies | CNPG promotes the replica; `feeddb-rw` follows; clients reconnect. 0 failed api requests measured. |
| Node drained for maintenance | Same as above. The drained node's instance waits for that node to come back, because storage is node-local (`local-path`, §5 #10). |
| migrate runs before the database is ready | `wait_for_db()` retries; the Job retries up to 10 times |
| Two deploys at once | Advisory lock: the second migration waits for the first |

## What `make verify` proves here ([`verify.sh`](../../../skypulse/scripts/verify.sh))

- ✅ api, analyzer and ingestor → PostgreSQL **allowed**
- ✅ Prometheus → database metrics (:9187) **allowed**; ❌ Prometheus → SQL (:5432) **blocked**
- ❌ api → database metrics **blocked** (only Prometheus may read them)
- ❌ `analysis` role **cannot** `DROP TABLE`; ❌ `ingestor` role **cannot** `DELETE FROM subscriptions`
- ✅ The owner Secret `feeddb-app` exists **only** in `skypulse-data`
- ✅ The database instances run on **different nodes**

## Design decisions behind it

[`skypulse/DESIGN.md`](../../../skypulse/DESIGN.md): D-2 (PostgreSQL as state store and queue), D-3 (CloudNativePG), D-8 (migrations in delivery), D-10 (database in its own namespace), D-11 (metrics from the database). Production: replicated storage, 3 instances, `ScheduledBackup` to on-site object storage with point-in-time recovery (§4).
